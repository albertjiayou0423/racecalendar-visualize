# 客户端辅助采集与持久化

## 客户端运行方式

`ClientCrawl` 在公开页面加载六秒后异步领取任务，不阻塞首屏。浏览器直接请求任务中固定的 Jolpica F1 赛历或单场 WRC 官方 feed，使用访客当前网络；没有调用服务器代理，也不携带第三方 Cookie、服务端密钥或用户资料。初版未接入 FE。

浏览器与全站分别限制每三小时一次：浏览器使用 localStorage 和会话内冷却；数据库以“系列 + 三小时 UTC 时间桶”为主键原子分配任务，每个系列每天最多八个任务，多个访客不能同时领取相同任务。任务令牌随机生成、只存 SHA-256 哈希，有效期两分钟且只能上传一次。F1 已达到原有每日配额时不分配。

每个数据源最多读取约 252 KiB，单次上游请求超时 12 秒，领取、最多两个上游与回传整体最多 35 秒。离线、省流量、2G 和隐藏标签页暂停；页面关闭后无法持续工作。无数据库时接口返回 503，不分配任务。失败、CORS 拒绝、超限或无效 JSON 不提交部分数据，不影响首页服务端获取链路。放弃的任务占用本次时间桶，下一桶才能重新领取。

2026-10-11 实际只检查了上游 HTTP 响应头：Jolpica 返回 `Access-Control-Allow-Origin: *`；WRC feed 返回 200 但没有该头，普通网页跨域读取会受限。尚未进行实际浏览器端到端验证。`no-cors` 无法让脚本读取响应；这项功能不能保证 WRC 在普通浏览器中成功，也不等于运行整个 WRC 服务端爬虫。

## 自动比较与补缺

`POST /api/client-crawl` 接收任务令牌和原始响应，限制请求体 256 KiB，检查同源、令牌、过期与重复上传。数据由服务端解析；客户端上传的名称、链接、赛事 ID 和其他元数据不直接采用。

F1 检查赛季、已知赛事 ID、重复轮次、合法 UTC 和场次日期范围，仅生成已知 F1 场次。WRC 复用服务端的官方 FAQ 行程解析器，并限定任务对应的已知赛事、日期范围与场次数量。

`fillClientGaps` 按赛事 ID 和场次名称匹配；WRC 以 SS 编号匹配，身份歧义时跳过。只新增缺失场次或填入无效 UTC。**已有有效 UTC（包括估计 UTC）均保持原值**，不修改现有赛事名称、转播、位置、时区、人工覆盖等元数据。已有数据完整则记录 `unchanged`，不新增赛历快照。

客户端内容无法仅凭结构校验证明来自官方，因此补入场次设置 `tentative=true` 与 `clientUploadedAt`，赛事保留 `clientData` 的来源 URL、上传时间与补充场次。首页 EventCard 显示小 `i`，支持悬停和点击展开说明。WRC 待核验场次仍显示“时间待确认”，不会自动成为官方已确认时间。不需要管理员选择或审批。

## 数据库保存机制

原有服务端抓取通过 `refreshSeries` → `fetchWithSnapshot`：成功且非空才保存；上游失败、成功空列表或异常保留最近成功快照，不写失败快照。F1 / FE 保存完整结果；WRC 保存前将本次估计场次与已有已确认场次合并，尽量保留真实历史时间。WRC 合并步骤报错时现有实现仍尝试保存本次数据，这是原有行为。

`crawl_snapshots` 使用 INSERT 追加 JSONB 完整系列快照、数据库生成的 `fetched_at` 和来源 `source`，没有自动清理。读取只选择 `ok=true`、events 非空的最新记录。写入失败向调用方传播；原有链路显示持久化失败。没有 `DATABASE_URL` 时原有获取仍可返回数据，但不持久化，也不持久化计数。

客户端补缺使用另一条严格路径：先读取成功快照，计算补缺，再在 Read Committed 事务中获取该系列的 PostgreSQL advisory lock，然后通过单条 CTE 同时保存新快照（`source=client-upload`）、任务状态/补缺摘要及 F1 配额计数。原有服务端快照写入也使用相同事务锁，因此等待锁后可检查其间提交的新快照；有更新则放弃客户端旧计算结果。写入时间使用 `clock_timestamp()`，避免等待锁的事务开始时间影响最新记录排序。数据库任何一步失败时事务回滚，接口不返回 `saved=true`。原有服务端配额查询和递增仍分开，整个项目尚未实现跨路径全局原子预留。

`client_crawl_jobs` 记录 assigned、processing、saved、unchanged、failed、invalid 或 superseded-or-quota 状态，可在后台数据库检查器中只读查看。没有人工审核表或采用按钮。极端写入失败可能留下 processing 状态，但不会假报快照保存成功。

客户端确认保存成功后通过 SWR mutate 重新读取 `/api/schedule`，已挂载的首页或详情可以收到新快照；平时 SWR 不主动轮询。服务端后续重新获取官方数据可替换客户端补充内容及标记。浏览器 localStorage / Service Worker 是展示与离线缓存，不能替代数据库持久化。没有访客就不采集，没有 Cron，也不会在构建时爬取。
